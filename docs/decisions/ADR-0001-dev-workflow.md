# ADR-0001: 개발·테스트 방식 — 데스크톱 시뮬레이션 + 주기적 Quest 단독 빌드

- 날짜: 2026-10-02
- 상태: 채택

## 배경

- 보유 XR 기기는 Meta Quest 3S 1대
- 개발 PC는 내장 GPU(Radeon 680M)뿐이다. Quest Link(PCVR)는 외장 GPU를 요구하므로 에디터 VR Preview로 바로 테스트하는 일반적인 방식을 쓰기 어렵다.
- 멀티플레이 2인 테스트가 필요하지만 헤드셋이 1대뿐이다.

## 검토한 대안

| 방식 | 장점 | 단점 |
|---|---|---|
| ① PCVR(Link) + 에디터 VR Preview | 반복 속도 가장 빠름 | 이 PC에서 사실상 불가 |
| ② 매번 Quest 단독(Android) 빌드 | PC 성능 무관, 최종 형태와 동일 | 빌드·설치에 매번 수 분, 반복이 느림 |
| ③ 데스크톱 시뮬레이션 + 주기적 Quest 빌드 | 로직·네트워크 작업을 헤드셋 없이 빠르게 반복 | 시뮬레이션 입력 Pawn과 도구를 직접 만들어야 함 |

## 결정

**③을 채택한다.**

- 데스크톱 모드: 마우스·키보드로 HMD와 양손 위치를 흉내 내거나, Quest에서 녹화한 트래킹 데이터를 재생한다.
- 기능이 한 단위 완성될 때마다 Quest 단독 빌드로 실기 검증한다.
- 2인 테스트는 Quest(클라이언트) ↔ PC 데스크톱(Listen Server)로 진행한다.

## 이유

- 헤드셋 1대 문제를 함께 해결한다. 데스크톱 클라이언트가 두 번째 플레이어 역할을 한다.
- 트래킹 녹화·재생 도구를 서버 검증 테스트에 재사용할 수 있다. 비정상 데이터를 일부러 재생해 검증 로직을 시험한다.
- 실제 Wi-Fi 환경에서 네트워크를 테스트하게 된다.

## 결과 및 주의점

- 트래킹 입력을 "기기 입력"과 "시뮬레이션 입력"으로 갈아끼울 수 있도록 **입력 소스를 추상화**해야 한다. (M1 설계에서 다룸)
- 실기 테스트 빈도가 낮아 VR 특유의 감각(멀미, 손 위치 어색함) 문제를 늦게 발견할 수 있다. 기능 단위마다 Quest 빌드를 거르지 않는다.
- RAM 13GB는 UE5 에디터 + C++ 빌드에 빠듯하다. 가능하면 RAM 증설을 고려한다.
